# pi-harness

A Pi extension that applies the harness-engineering practices from
[`walkinglabs/learn-harness-engineering`](https://github.com/walkinglabs/learn-harness-engineering)
inside Pi.

It scaffolds a per-project "harness" folder (instructions, feature tracker,
progress log, verification script, session handoff, docs) and, once a harness
is active, injects its location into the system prompt on every turn so the
agent reads the harness files by default — no need to repeat the path.

## Layout

```
~/pi-harness/                 # HARNESS_ROOT (override with PI_HARNESS_ROOT)
└── <project-name>/
    ├── AGENTS.md             # instructions (rename via --agent-file)
    ├── index.md              # map of the harness
    ├── feature_list.json     # feature tracker (status + evidence)
    ├── feature-list.schema.json
    ├── progress.md           # current state / next steps
    ├── session-handoff.md    # blockers, files touched, next session
    ├── init.sh               # verification entrypoint (fail-fast); optional via --no-init
    ├── clean-state-checklist.md
    ├── evaluator-rubric.md
    ├── quality-document.md
    └── docs/
        ├── ARCHITECTURE.md
        ├── CODE-STYLE.md
        ├── PLACEMENT.md
        ├── PRODUCT.md
        └── SOURCE-MAP.md   # generated by /ha-learn
```

State (active project + registry) lives at
`~/.pi/agent/pi-harness-state.json`.

## Commands

| Command | Purpose |
|---|---|
| `/ha-init <name> [--force] [--no-init] [--agent-file=CLAUDE.md] [--project-root=/path]` | Scaffold `~/pi-harness/<name>` and make it active (`--no-init` skips `init.sh`) |
| `/ha-use [name]` | Switch the active harness (picker when no name) |
| `/ha-list` | List harness workspaces |
| `/ha-status [name]` | Show active harness + feature state |
| `/ha-learn [name] [--root=/path] [--scan-only] [--max-files=N]` | Scan the source code and seed the harness docs + feature candidates |
| `/ha-edit [name] [--name=NEW] [--path=/new/dir] [--project-root=/src]` | Rename a harness and/or change its workspace path or source root |
| `/ha-validate [name]` | Score the harness across the five subsystems |
| `/ha-disable` | Turn pi-harness off (stop harness injection) |
| `/ha-enable` | Turn pi-harness back on |

```bash
# Scaffold + activate
/ha-init my-app

# Study the code and fill the harness
/ha-learn my-app                 # scan, then let the agent refine the docs
/ha-learn my-app --scan-only     # scan only, no agent pass
/ha-learn my-app --root=/path/to/repo
```

`/ha-learn` is the "study the source code" command. It teaches the agent the
project's **code style** (`docs/CODE-STYLE.md`) and **where new files belong**
(`docs/PLACEMENT.md`), so a new controller, service, model, or test lands in the
right place and matches the surrounding conventions. It:

1. Walks the source tree (ignoring `node_modules`, build dirs, lockfiles, …).
2. Detects languages, directory roles, entry points, dependencies, configs, tests, TODO/FIXME markers, and git state.
3. Samples up to 40 representative source files to detect the house **code style**: indentation, quotes, semicolons, line width, module system, file/type/function/variable naming, comments, error handling, async style, and formatting/linting tools.
4. Infers a **placement guide**: which directory each kind of file belongs in (controller/handler, route, service, model, repository, schema, component, hook, store, middleware, util, config, migration, test, CLI) plus the naming pattern of its existing files.
5. Writes real content into `docs/ARCHITECTURE.md`, `docs/CODE-STYLE.md`,
   `docs/PLACEMENT.md`, `docs/PRODUCT.md`, `docs/SOURCE-MAP.md`,
   `quality-document.md`, `progress.md`, and `index.md`.
6. Merges discovered work into `feature_list.json` as `not-started` candidates
   (existing features are never overwritten).
7. Unless `--scan-only` is passed, sends the agent a deep pass that reads 5-10
   representative files and rewrites the architecture, code-style, and placement
   docs with confirmed conventions and canonical examples.

`/ha-edit` manages existing harnesses without recreating them:

```bash
/ha-edit old-name --name=new-name      # rename (moves the workspace folder)
/ha-edit my-app --path=/custom/dir     # move the workspace folder
/ha-edit my-app --project-root=/src    # repoint the scanned source root
/ha-edit my-app --name=new --project-root=/src   # combine
```

Renaming/moving updates the registry and the active pointer, and the folder
contents are preserved. If the target name or path already exists, the edit is
rejected.

Start Pi with `--no-harness` to disable pi-harness for a single run without
changing the persisted setting. `/ha-disable` and `/ha-enable` persist the
toggle in `~/.pi/agent/pi-harness-state.json`.

## Tool: `harness`

- `info` — active harness paths + feature summary
- `list` — every harness project
- `read { file }` — read a harness-relative file (path-escape safe)
- `features` — list features with status
- `update-feature { featureId, status?, evidence? }` — update the tracker; `status: "done"` requires evidence
- `learn { root? }` — scan the source code and seed the harness
- `edit { newName?, path?, projectRoot? }` — rename/move a harness or repoint its source root
- `validate` — five-subsystem score (instructions, state, verification, scope, lifecycle)
- `enable` / `disable` — toggle pi-harness on or off

## Automatic lookup

Two hooks make the harness the default place to look, and by default the
harness is chosen by **name matching the active repo**:

- `session_start` — resolves the active harness in this order:
  1. If the cwd is inside `~/pi-harness/<name>`, that harness wins.
  2. Otherwise it takes the enclosing git repository's name (falling back to
     the cwd basename) and activates the harness with the same name
     (case-insensitive; `_`/`-` tolerant).
  3. If no harness matches, pi-harness stays **off for the session** —
     nothing is injected until a matching harness exists (create one with
     `/ha-init <name>`).
- `before_agent_start` — injects a `harness_state` system-prompt section with
  the harness root, key files, and current feature state, **and loads the
  harness instruction file (`AGENTS.md`/`CLAUDE.md`) as project context** so it
  is always read by default.

The harness instruction file takes precedence over the code repo's own
`AGENTS.md`/`CLAUDE.md`: its context entry is moved to the front and the repo's
copy is dropped for the run. User-level instructions outside the project and
harness roots (for example `~/.pi/agent/AGENTS.md`) are preserved. Set
`PI_HARNESS_KEEP_PROJECT_AGENTS=1` to keep the repo's own `AGENTS.md` alongside
the harness one.

The persisted `/ha-disable` toggle and the `--no-harness` flag still win over
auto-selection.

Set `PI_HARNESS_ROOT=/some/path` to move the root out of `~/pi-harness`.
